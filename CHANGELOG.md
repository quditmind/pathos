# Changelog

All notable changes are listed here. Versions follow [Semantic Versioning](https://semver.org/); before 1.0, minor versions may contain breaking changes.

## [Unreleased]

### Fixed
- **upgrade.sh and backup.sh reported the target version as the current one**: with `--pull`, the "current" version came from the configured image (already the new release), so the log said e.g. "3.0.1 -> 3.0.1" and the pre-upgrade backup manifest recorded the new version. Both now ask the running api container and fall back to the image only when api is not running. Restores were not affected (they use the schema version).

### Security
Findings from a PATHOS self-scan (Comprehensive profile on this repository):
- **Release workflow**: GitHub expressions (`github.ref`, matrix values, step outputs) are no longer expanded inside `run:` scripts; they are passed as environment variables (zizmor template-injection, 4 high). The release job no longer restores a Go build cache, so a poisoned cache entry cannot reach the signed CLI binaries (zizmor cache-poisoning, high).
- **golang.org/x/crypto 0.58.0 → 0.59.0** (GO-2026-5932, the deprecated `openpgp` package; PATHOS does not import it).
- **wcmatch 8.5.2 → 11.2** in the sast and mobile workers (CVE-2026-132276, a ReDoS on file names, which scanned repositories control). Semgrep gives the same results with both versions.
- **Smoke test verifies TLS certificates** (against `PATHOS_CA_CERT`, the bundled Caddy proxy's local CA, or the system trust store) instead of disabling verification.
- **Bitbucket Pipelines template** and its user-guide example pin the Semgrep image by version and digest instead of an untagged image.

## [3.0.1] — 2026-11-21

### Fixed
- **Sidebar wording for modules that are switched off**: a built module whose feature flag is off was shown as "arrives in roadmap phase N", as if it were not built. It now shows an **Off** label and "not enabled. An administrator turns it on in Administration › Feature flags". The Feature flags page note and the System status Connectors row no longer refer to roadmap phases.

## [3.0.0] — 2026-11-21

PATHOS 3.0: the nine-phase application security lifecycle (milestones M0–M10, sections below), the 2.2.1–2.2.3 fixes, and patched worker image dependencies. Every new module is behind a feature flag, off by default; with all flags off 3.0 behaves like 2.2.3 and keeps every page and URL. Upgrading from 2.2.x is supported (migrations 00043–00067, additive; see *PATHOS 2.2.1–2.2.3 brought forward into 3.0*).

### Security
- Worker image dependencies patched (Dependabot alerts on the worker manifests; the deliberately vulnerable fixtures under `benchmarks/` and `e2e/tests/fixtures-data/` are unchanged):
  - worker-sca: package.json `overrides` pin body-parser 2.4.0 (CVE-2026-111181; an optional cdxgen dependency that `npm ci --omit=optional` does not install), glob 14.0.6 (CVE-2026-118773) and minimatch 11.0.9 (CVE-2026-118764) for cdxgen and its `@npmcli` helpers; no cdxgen release ships them yet. The copies bundled inside npm 12.2.3 itself stay at glob 13.0.6 and minimatch 10.2.5 until npm ships a release with them.
  - worker-dast: tornado 6.5.10 → 6.6.1 (CVE-2026-116577, CVE-2026-116578, CVE-2026-115927, CVE-2026-126347), installed with `--no-deps` over mitmproxy 12.3.1's `tornado<=6.5.10` pin; only mitmproxy's interactive UIs import tornado, and Wapiti uses mitmproxy's core only.
  - worker-sast and worker-mobile: PyJWT 2.14.0 → 2.15.1 (CVE-2026-101918, CVE-2026-102275) and the OpenTelemetry packages 1.37.0 / 0.58b0 → 1.45.2 / 0.66b2 (opentelemetry-api CVE-2026-114603, CVE-2026-126360), plus opentelemetry-exporter-http-transport and opentelemetry-exporter-otlp-common, which the 1.45 OTLP exporter needs; installed with `--no-deps` over semgrep 1.172.0's pins, like the existing mcp and PyJWT overrides.

### Fixed
- **Sandbox e2e scripts** (`workers/fuzz/test/sandbox-e2e.sh`, `workers/rea/test/rea-e2e.sh`) wait until the stand-in egress and API listeners accept connections before starting the worker (CI flake: "control: egress:3128 not reachable from the worker: connection refused").
- **binwalk in `worker-rea` could exit successfully having analysed nothing** (flaky "Reverse-engineering sandbox" CI step: `firmware: entries []`, binwalk "succeeded" in 7 ms). binwalk 3.1.0's main loop waits on `ThreadPool::active_count()`, which does not count a job no pool thread has picked up yet nor a result still in the channel; on a busy CPU it exited 0 before analysing the input, or before analysing files it had extracted, without logging them. The image now builds binwalk 3.1.0 from the crate pinned by its crates.io SHA-256 with `workers/rea/binwalk-worker-pool-race.patch` (the loop counts the jobs whose results it has not received). Under CPU contention the unpatched binary lost results in 8 of 500 runs at 2 CPUs and 254 of 500 at 1 CPU (205 with no analysis at all); the patched one in none of 1,000. With the sandbox runner sharing its CPUs with busy loops, `rea-e2e.sh` reproduced the CI failure with the old image (1 of 8 runs) and passed 25 of 25 runs with the fixed one.
- **pathos-rea no longer reports an incomplete binwalk run as a success**: a run without an analysis of the input in binwalk's log, or with extracted files queued for recursive analysis but never analysed, is reported as binwalk `failed` with the reason (what it did find is kept), never as `succeeded` with empty results. binwalk's log is parsed as binwalk 3.1.0 actually writes it (`[{a}],{b}],{c}]`: it opens the log in append mode); before, only the first analysis was read.

### PATHOS 2.2.1–2.2.3 brought forward into 3.0

The 2.2.x maintenance fixes (sections [2.2.3], [2.2.2] and [2.2.1] below) are part of 3.0. What changed in carrying them over:

- **Migrations renumbered**: 2.2.x migrations 00043 (scan concurrency) and 00044 (anonymous repositories, private CA bundles, secret exclusions) are **00066** and **00067** in 3.0, because 3.0 had used 00043 and 00044 (feature flags, connectors). Both are idempotent. An upgrade from 2.2.2 or 2.2.3 releases the 2.2.x rows of versions 43 and 44 in `goose_db_version` when the 3.0 table of that number does not exist (`backend/internal/platform/db/reconcile22.go`), then applies 00043–00067; the 2.2.x objects and their data are kept. Fresh installs and upgrades from 2.2.3 are covered by `backend/test/integration/upgrade22_test.go`.
- **Scan concurrency with reverse engineering**: `scan_jobs_running_uq` is one running repository scan (or CodeGraph discovery) per repository, pull request and lane; `scan_jobs_running_target_uq` one running scan per target and lane; reverse-engineering analyses keep their own lane.
- **Error codes** use the 3.0 diagnostic envelope (`httpx.Error.WithDiag`; 2.2.x `WithErrorCode`) and are in the catalogue with troubleshooting pages: `PTH-ONB-1101`–`1106` (anonymous import), `PTH-CONN-1701`/`1702` (private CA bundle invalid / untrusted certificate), `PTH-SCAN-1101` (profile tools no worker has). The planned SIEM codes of the integration spec move from `PTH-CONN-1701`–`1703` to `PTH-CONN-1703`–`1705`, since the released 2.2.x codes keep their numbers.
- **Connectors hub**: registry connections, outbound webhooks and ticket connections show whether a private CA bundle is set (`ca_bundle_set`), and a health check that fails on an untrusted certificate of such a connection reports `PTH-CONN-1702` (add the CA bundle on the connection); SCM connections keep `PTH-CONN-1004`.
- **Anonymous repositories and Generic Git**: an anonymous public repository (`source_type` `git`, no connection, no credential) and a 3.0 Generic Git repository (`source_type` `scm`, an SCM connection of provider `generic_git` with a credential) are distinct; both are kept.

### PATHOS 3.0 M9 — Reporting and monitoring

Migrations 00064–00065 are additive: new tenant tables `monitoring_events`, `architecture_drifts` and `monitoring_settings` (standard row-level security policy), the column `remediation_items.threat_id` and the verification trigger `fix_submitted`. The feed, drift, drift alerts and the new feedback-loop behaviour are behind the `continuous_monitoring` feature flag (off by default); with the flag off every module behaves as in M8.

#### Added
- **Continuous monitoring** (`/monitoring`, "9 · Report & monitor", [user guide](docs/user-guide/monitoring.md), [API](docs/api-reference/monitoring.md)): a per-organization feed of the lifecycle feedback loops and other changes, filterable by application, severity, type, loop and time, with keyset pagination, a summary and a version-stamped CSV export; every event states its evidence label and references (snapshot ids, commit, scan, decision, verification). The application hub's Overview has a Monitoring card (latest events and drift).
- **Architecture drift**: every new CodeGraph snapshot is compared with the previous one of the repository — routes, API operations, external services, datastores, queues, internet exposure, trust-boundary crossings and components added, removed or changed — with the CodeGraph evidence of each item; a drift timeline per application and a detail drawer. **Drift alerts** through the existing notification channels (new event `architecture.drift`, seeded rule, webhooks) are off by default and configured in the page.
- **Feedback loops 1–7 wired and tested end to end** (`backend/test/integration/m9_monitoring_test.go`): (1) push/new commit → scan → CodeGraph rediscovery; (2) dependency change between snapshots → component policies re-evaluated and dependency findings re-scored; (3) architecture change → threat model draft regenerated as a new version (approved versions never change) or flagged for review; (4) new intelligence (EPSS, KEV, OSV) → findings re-scored and listed; (5) fix pull request merged or item marked *fix submitted* → targeted verification rescan; (6) gate failure under a policy → developer feedback (pull request check as before, new notification event `gate.failed` in-app/e-mail/webhooks); (7) new findings → AI triage queue → automated AI review with an M7 AI evidence record (prompt, response, model; `ai.triage_concluded` in the feed points at it), never auto-approved with monitoring on — a false-positive verdict always waits for a person — and secret values never sent.
- **Report upgrades**: technical reports (`/ai/reports`) and the compliance framework detail carry lifecycle evidence sections — CodeGraph, threat models, remediation, gates — each stating where its figures come from and why a section is unavailable; compliance exports `GET /api/v1/compliance/frameworks/{key}/export?format=json|csv`.
- **Version stamps on every export**: server downloads go through `httpx.Download` (`X-PATHOS-Generated-By`, `X-PATHOS-Version`, `X-PATHOS-Build`; JSON documents also carry `generated_by`); a unit test fails if a handler sets `Content-Disposition` without the stamp, and an integration test walks the export endpoints. Browser exports carry version and build in the file name (and graph JSON in `generated_by`); printed pages show the stamp in a print-only footer.
- **Remediation ↔ threats**: items of kind `threat_mitigation` reference an M5 threat (`threat_id` on create, patch and list filter; `threat` on items; `remediation_items` on `GET /api/v1/threats/{id}`); the item page links and unlinks a threat, the threat detail lists its items and creates one.
- **Smoke test**: the tool-version check reads the core worker and its tool count is a lower bound (family workers such as `worker-graph` and `worker-rea` report their own tools); both Mailpit checks honour `PATHOS_MAILPIT_URL`; 21 built-in notification rules.
- 7 catalogue codes: `PTH-MON-1101`–`1105`, `PTH-REM-1107`, `PTH-REP-1101`, with regenerated troubleshooting pages.

#### Changed
- **Lifecycle overview** (backend `inventory/lifecycle.go` and the hub strip): Discover counts CodeGraph snapshots, Threat model counts models and open threats, Remediate & gate counts remediation items and gate decisions, Report & monitor counts monitoring events and drift; built modules never say "arrives in"; phases without data say so.
- Threat model auto-update returns its outcome per model (`AutoUpdate`); models whose latest version is in review, or with automatic updates off, are reported as needing review instead of being skipped silently.
- Two new seeded notification rules ("Failed security gates", "Architecture drift alerts"); notification events `gate.failed` and `architecture.drift` are raised only with the flag on.
- The cross-tenant isolation suite enables `continuous_monitoring`, maps `drift`, seeds organization B with events, drift and settings, and adds `threat_id` to the body references (remediation items are created as threat mitigations of a seeded organization A threat, so the probe keeps a valid control); with M7 and M10: 530 routes, 7,352 requests per layer, 172 of 173 write routes reach the organization check, 16 parent-in-body controls with row-level security (14 application only); the route-scan floor is raised to 530.

### PATHOS 3.0 M10 — Reverse engineering, static tier

Behind the `reverse_engineering` feature flag (off by default). Migrations 00061–00063 are additive (five new tables; new columns `scan_targets.provenance_material` and `codegraph_snapshots.kind`; `scan_jobs.trigger` accepts `rea`; new CodeGraph node, edge and evidence kinds). Done-when: analyses run only on artifacts from the organization's own builds by default.

#### Added
- **Input policy**: an artifact is analysed only when PATHOS can tie it to the organization's own builds — a verified signature or a verified SLSA provenance attestation (the attested subject must be the artifact's SHA-256), recorded by the existing cosign check of target scans. Anything else needs an explicit per-artifact "analyse untrusted artifact" authorisation (new permission `rea.authorize`, a reason, bound to the SHA-256, audited); the stricter policy "own builds only" refuses authorisations. Refusals answer `403 PTH-REA-1001` and are audited.
- **Provenance attestations for build artifacts**: artifact and mobile app targets accept a `provenance` bundle (`cosign attest-blob --bundle`) at upload or as `provenance_material`, verified with `cosign verify-blob-attestation` when the target's policy sets a `slsaprovenance*` attestation type.
- **`worker-rea` family image** (`workers/rea`, Compose profile `rea`): a standalone image with `pathos-worker`, the `pathos-rea` analyser, radare2 6.2.6 (LGPL-3.0), binwalk 3.1.0 (MIT) and ilspycmd 11.2 (MIT), pinned and checksum-verified (253 MB, 0 fixable HIGH/CRITICAL in Trivy); Ghidra 12.2 headless (1.43 GB, passes the gate) and Jadx 1.5.7 (fails the gate: bundled Guava) as optional build arguments; Joern and angr not included (size). The analyser never executes the artifact and runs only in the sandbox runner `worker-rea-sandbox` (no network, UID 10002, read-only, no capabilities, CPU, memory and pids limits); the agent is on the internal worker API network only. Analyses have their **own queue lane**: only workers that advertise `pathos-rea` lease them, those workers lease nothing else, and an analysis neither waits for nor blocks the repository's scans.
- **Normalised facts**: sections, functions (exact Go symbol names from the Go symbol table), imports and linked Go packages, exports, strings with secrets redacted (by the analyser and again by the API), the call graph and string references, firmware entries and extracted files, Go build information, and code views (disassembly, or pseudo-C from the decompiler) for selected functions.
- **Binary graph in the CodeGraph store**: snapshots of kind `binary` with node types `binary`, `binary_function`, `import`, `string_ref` and `section`; every edge `verified` with evidence of kind `binary` (file offset and tool), enforced by the database. Binary snapshots never appear among an application's source snapshots and are never used by threat models.
- **Source ↔ binary diff** against the CodeGraph snapshot of the artifact's commit (from the provenance, the binary's Go build information, or a snapshot a person chooses): the artifact's own functions, linked packages, routes and URLs that are only in the binary, only in the source, or matched, each with evidence. CodeGraph discovery now records sensitive standard-library imports per Go file (`sensitive_imports`), so a debug handler only in the binary is explained by its import line.
- **Finding drafts** for sensitive binary-only items (debug endpoints such as `net/http/pprof` and `expvar`, command execution, dynamic loading, weak cryptography, unbounded string functions, privilege changes): proposals labelled as such; a person creates the finding (status `needs_review`), dismisses the draft with a reason, or adds a threat to the application's threat model (M5).
- **Settings** (Configurations → Reverse engineering tools): enabled tools, memory and time limits, input policy, and which AI model may see decompiled code (default none; local only; cloud only while the AI configuration allows sending code).
- API under `/api/v1/rea` ([API reference](docs/api-reference/reverse-engineering.md)); permissions `rea.run` and `rea.authorize` ([RBAC matrix](docs/RBAC_MATRIX.md)); error codes `PTH-REA-1001`…`1012` ([troubleshooting](docs/troubleshooting/rea.md)); design: [PATHOS_REVERSE_ENGINEERING.md](docs/aspm/PATHOS_REVERSE_ENGINEERING.md).
- Web app: **Binary analysis** (sidebar group 5) with the artifact list, trust badges and the authorisation dialog, and the analysis workspace (Functions, Call graph on the shared graph component, Strings & imports, Runtime behaviour — "Sandbox tier arrives after 3.0", Source ↔ binary with proposals, History); **Reverse engineering tools** in Configurations. Help: [user guide](docs/user-guide/reverse-engineering.md) with Troubleshooting, mapped to every new route.
- Tests: analyser unit tests; the real image on a C ELF and a Go binary built in the test and on a firmware blob made from test data, plus an isolation probe through the real sandbox runner (`workers/rea/test/rea-e2e.sh`); backend unit tests (document validation and redaction, binary evidence on every edge, the diff on a Go binary with a planted pprof import, drafts, settings and the decompiled-code policy, provenance parsing, blob attestation verification, the worker tool never running without the sandbox); an integration test of the whole flow (unsigned artifact refused by default and nothing queued, authorisation rules, provenance verified through the cosign result, the lanes, ingest, facts, graph, diff, drafts, finding creation); the tenant isolation suite covers every new route; frontend unit tests; Playwright `e2e/tests/reverse-engineering.spec.ts` with light and dark screenshots.

#### Changed
- `scan_jobs_running_uq` allows one running execution per repository and lane (reverse engineering or not).
- The CodeGraph graph and node inspector handlers are shared with binary graphs (`graphOf`, `nodeOf`); source snapshot queries filter `kind = 'source'`.
- Binary snapshots are excluded from the M7 cross-phase correlation and the AI review's CodeGraph context (`kind = 'source'`), like every CodeGraph and threat-model query.
- Lifecycle phase 5 (Reverse engineering) is available: it counts the application's completed binary analyses (`binary_analyses`; restricted without `findings.read`).
- The *Reverse engineering* kind of check names `pathos-rea` as its PATHOS engine (`checkKinds.json` regenerated); the catalogue has 100 integrations.
- **CI e2e workers**: the CI stack job starts `worker-graph`, `worker-rea` and `worker-rea-sandbox` and seeds the PATHOS repository as an application (`scripts/seed-e2e-app.py`), so the CodeGraph, threat-model and reverse-engineering browser tests run against the real workers (estimated +3–5 minutes; see CONTRIBUTING.md).
- Rule 3: Configurations › Reverse engineering tools joins the pages that may name tools (decision C5); ADR-009 is approved as built, with its decisions recorded in the ADR.
- The release workflow builds, signs and pushes `pathos-worker-rea`; its verification notes list `pathos-worker-graph` and `pathos-worker-rea`.
- The cross-tenant isolation suite enables `reverse_engineering` through `isolationFlags`, maps `artifacts`, `authorizations`, `analyses`, `drafts` and `functions`, seeds reverse-engineering rows of organization B and a scan target of A, requires the five reverse-engineering write routes to reach the organization check, and raises its floors to the measured 172 write routes and 14 parent-in-body controls.

### PATHOS 3.0 M7 — AI security intelligence

Behind the `ai_intelligence` feature flag (off by default) for the new API and pages; AI evidence records are written for every AI call whatever the flag. Migrations 00058–00060 are additive (four new tables, nullable link columns, a foreign key on `threats.ai_evidence_id`, the threat event `ai_accepted`).

#### Added
- **AI evidence records** (ADR-008, [PATHOS_AI_SECURITY_INTELLIGENCE.md](docs/aspm/PATHOS_AI_SECURITY_INTELLIGENCE.md)): one record per AI decision or conclusion PATHOS stores (AI reviews, MCP reviews, Human Eye suggestions, analyst answers, report narratives, fix proposals, troubleshooting answers, threat suggestions, correlation explanations, replays) with the subject and related CodeGraph nodes and edges, the reasoning steps, conclusion, verdict and confidence, the model, reported version and provider (local or cloud), the parameters, the SHA-256 of the prompt and the response, the reviewer and decision, and timestamps. The redacted prompt and response are stored envelope-encrypted for 180 days by default (configurable per organization), purged by the jobs service and rewrapped by `pathosctl rotate-master-key`; records are deleted with their finding and are immutable except the review. Failed and refused calls are recorded too. A unit test parses the backend and fails when a model call bypasses the recorder or a call path has no completeness test.
- **Reproduce**: replays the stored prompt with the same configuration version, model and parameters (temperature 0 and a seed on local models) and compares the answers (same conclusion, identical response, model changed, steps added and removed); every record states whether the provider can repeat its answer. 30 replays per organization per hour.
- **Model per task**: an AI configuration per task (triage and review, fix proposals, troubleshooting, threat suggestions, correlation, analyst chat, report narratives); code-bearing tasks default to a self-hosted model when one exists. Source code is sent only where the configuration's *Send code context* allows it; a request that needs code is otherwise refused and recorded (`PTH-AI-1101`).
- **Cross-phase correlation** `GET /api/v1/findings/{id}/correlation`: the finding's CodeGraph nodes and edges, threat-model threats, SBOM components, runtime context and related findings, joined deterministically with evidence labels; `POST …/correlation/explain` adds an AI-inferred explanation and priority with its evidence record.
- **AI threat suggestions** `POST /api/v1/threat-models/{id}/suggest` (the M5 reserved AI path): AI-inferred threats in the draft, each with its own evidence record, kept only when they name diagram elements; accepted or rejected one by one (rejected ones leave the draft); a draft with pending suggestions cannot be submitted (`PTH-AI-1302`).
- API `/api/v1/ai/evidence`, `/api/v1/ai/task-assignments`, `/api/v1/ai/evidence-settings` ([API reference](docs/api-reference/ai-evidence.md)); permission `ai.evidence_read` (in every built-in role, [RBAC matrix](docs/RBAC_MATRIX.md)); error codes `PTH-AI-1101`…`1103`, `PTH-AI-1201`…`1205`, `PTH-AI-1301`, `PTH-AI-1302` ([troubleshooting](docs/troubleshooting/ai.md)).
- Web app: **AI evidence log** (7 · Validate & intelligence), an **AI evidence** panel in the finding drawer and the threat detail (AI-inferred label until a person confirms, Accept and Reject, prompt and response, Reproduce with the comparison), a **Correlation** section in the finding drawer, **Suggest threats with AI** on threat-model drafts, **Model per task** and **AI evidence** retention in AI settings. Help: [user guide](docs/user-guide/ai-security-intelligence.md) with Troubleshooting.
- Tests: call-site enumeration, interpreters, determinism and comparison unit tests; an integration test with stub providers covering record completeness on every call path, reproduce (local and hosted), retention and deletion with the finding, key rotation, model per task and code never sent to a cloud model without permission, no silent suppression, and the suggestion flow; the tenant isolation suite over every new route; frontend unit tests; Playwright `e2e/tests/ai-evidence.spec.ts`.

#### Changed
- **No silent suppression**: an AI review's *false positive* verdict always waits for a person's approval, whatever the configuration's approval policy (policies `never` and `false_positives` used to apply it directly on non-critical findings). *Needs review* still applies directly under `never`.
- AI reviews, Human Eye suggestions, analyst answers, AI reports and AI fixes reference their evidence record (`evidence_record_id`); AI troubleshooting answers return it. Threats return `ai_evidence_id` and `ai_review`; model counts `ai_pending`.
- With the flag on, AI review, assistance and fixes use the triage and fix tasks' configurations (a self-hosted one by default) instead of always the default configuration. With the flag off nothing changes.
- Integration with M8 and the lifecycle: the *Validate & intelligence* phase of the lifecycle overview and the application profile counts the AI evidence records of the application's findings (`ai_evidence_records` metric). Rule 3: the AI evidence log, the AI evidence panel (prompt, response, replay comparison) and the cross-phase correlation show the kind of check instead of scanner tool names (prompts carry the finding's engine and model answers may repeat it); the rule-3 test covers these pages. The cross-tenant isolation suite enables `ai_intelligence` through `isolationFlags`, maps the AI evidence routes and requires the evidence review, replay, correlation explanation and threat suggestion routes to reach the organization check.

### PATHOS 3.0 M8 — Remediation and gates

Migrations 00055–00057 are additive: new tenant tables `remediation_items`, `remediation_item_findings`, `remediation_verifications`, `remediation_views`, `security_gates`, `gate_decisions` and `gate_exceptions` (standard row-level security policy), columns `security_policies.managed_by`/`managed_repository_id`, `pr_checks.gate_mode`/`gate_decision_id` and `repositories.pr_gate_mode`. The workspace, gates API and the merged-fix feedback loop are behind the `remediation_workspace` feature flag (off by default). Pull request checks use the gates engine whatever the flag, with the same results as before (decision C6 below).

#### Added
- **Remediation workspace** (`/remediation`, [user guide](docs/user-guide/remediation.md), [API](docs/api-reference/remediation-and-gates.md)): one item per finding or per group of findings of a repository, with owner, due date from the SLA engine (or set by hand), status, root cause, secure fix guidance gathered from what PATHOS already holds (verified AI fixes, dependency upgrade targets via `internal/depfix`, Human Eye and applied AI review guidance, the advisory), each labelled *verified*, *scanner*, *human* or *AI-inferred*, affected files, the fix pull request (linked or found through the findings) and the verification history. Server-side filters and sort, saved views (private or shared), bulk assign/status/priority/due date.
- **Fix verification with before-and-after evidence**: *Verify fix* queues a targeted rescan that a worker runs with the verified-AI-fix machinery (`internal/aifix`, worker `scanFiles`): the findings' scanners on the affected files only, at the commit where they were last reported and at the head of the scan branch. Results: `fixed` (the item closes), `still_present`, `regressed` (new results in the affected files are listed), `inconclusive`; scan ids, commits, result counts and per-finding status before and after are recorded and immutable. A finished scan of the scan branch can serve as the evidence instead. An item closes only on proof (database CHECK); findings are still resolved only by scans. New worker endpoints `remediation-lease` and `remediation-jobs/{id}/result` ([worker protocol](docs/api-reference/worker-protocol.md#fix-verification-jobs-remediation)).
- **Who verifies**: the item's assigned owner may verify their own item with `remediation.read` alone (the rescan covers only the item's affected files); everyone else needs `remediation.manage` and `scans.run` on the repository. The detail returns `can_request_verification`.
- **Fix merged → targeted rescan**: the jobs service queues a targeted rescan for every item whose fix pull request was merged after its last verification.
- **Security gates at every stage** — IDE, pre-commit, pull request, CI, release, deploy: a gate applies an existing security policy in mode block, warn or require approval; `POST /api/v1/gates/evaluate` records a decision (`pass`, `warn`, `block`, `approval_required`, `exception_applied`) with reasons, policy ids and versions and evidence; decisions log with filters; gates CRUD (`gates.manage`). Release and deploy gates are called from CD (generic `curl` and an Argo CD `PreSync` hook Job are documented); no agent is installed.
- **Rule 7, enforced**: a gate cannot exist without a policy, and the database refuses a `block` or `approval_required` decision without a policy id (`gate_decisions_block_needs_policy`); the service downgrades any such result to `pass` (`no_policy_downgraded`); with no gate the decision is `pass`, recorded as `no_policy`. Integration tests enforce it.
- **Exceptions and approvals** with an expiry (at most 365 days), scoped to the decision's pull request or commit or to the repository, decided by someone other than the requester (`gates.approve_exception`; database CHECK), every request and decision audited.
- **`pathos gate --stage ide|pre-commit|pull-request|ci|release|deploy`** (`--repo` or `--application`, `--commit`, `--scan`, `--pull-request`): exit 1 on block or approval required. Without `--stage` the command is unchanged.
- **Permissions** `remediation.read` (every role), `remediation.manage`, `gates.manage` (organization-only) and `gates.approve_exception` ([RBAC matrix](docs/RBAC_MATRIX.md)).

### Added
- **Verified AI fixes** (migration 00033): **Propose fix** in the finding drawer of SAST, secrets and IaC findings asks the default AI configuration (any provider, including a self-hosted model) for a unified diff, built from the finding and the redacted code around it. PATHOS rejects diffs outside the finding's file (or two files next to it), over the size limits, or touching CI files, build scripts or dependency manifests unless the finding is in them. A worker applies the diff to a fresh checkout of the scanned commit and re-runs the finding's scanner on the changed files before and after: the finding must be gone and nothing new may appear. When an administrator chooses a test runner for the repository (`go` or `python`, off by default), worker-fuzz also runs the repository's tests without and with the fix in the sandbox runner. Only a verified fix can be opened as a pull request (`pathos/fix/ai-…`, fix pull request machinery), by a person; nothing is merged and the finding is resolved by a later scan. ### Changed
- **Security: repository code runs in a network-less sandbox runner.** The fuzzers of `worker-fuzz` (Go native fuzzing, Atheris) no longer run in the worker container, which is on the egress proxy and worker API networks and holds the worker token. ### Security
- Repository-wide `.gitleaks.toml` allowlists only the files that hold fake test credentials; the pre-commit Docker hook pins Gitleaks by digest.
- Fix pull requests never run repository code or package managers, and never write outside `pathos/fix/` branches.
- Commit author names are stored only while developer attribution is on; e-mail addresses are never stored.

### Known limits
- Fix pull requests do not support Go, Cargo, Composer, Bundler or npm/yarn/pnpm projects with a lockfile, or transitive dependencies.
- Push-event secret scanning alerts after the push (blocking needs the hooks) and supports GitHub and GitLab only.
- Material changes and licence findings are computed for branch scans, not pull request scans; no AI summary of material changes.
- Keyless signature verification is skipped offline; shallow clones record the introducing commit as unknown.
- The VS Code extension, CI templates and pre-receive hook are tested in isolation, not yet against live services.
