# Secret references (Vault / OpenBao)

Quditmind PATHOS · applies to v3.0 (Unreleased, milestone M2) · status: Prototype (behind the **Connectors** feature)

## Purpose

Some organizations do not want connector credentials (SCM tokens, ticketing tokens, webhook URLs, SMTP passwords) stored in PATHOS, even encrypted. With a **secret reference**, PATHOS stores only where the secret lives:

```
vault:<mount>/<path>#<key>
```

for example `vault:secret/pathos/scm/github#token`. Whenever PATHOS needs the credential, it logs in to Vault (or OpenBao), reads the KV version 2 secret `<mount>/data/<path>` and uses field `<key>`.

## Scope

- Works with **HashiCorp Vault** and **OpenBao** (an open-source fork that implements the same HTTP API). PATHOS bundles neither; it speaks the HTTP API only.
- Secret engine: **KV version 2**. The field must be a string.
- Authentication of PATHOS to Vault: **AppRole** or **Kubernetes** auth.
- A reference can replace any *single-value* credential that an administrator types into a connector: a personal or HTTP access token, an API key, a password, an outbound webhook URL. For a user name + token credential (Generic Git over HTTPS, a Bitbucket Data Center user token, a Bitbucket Cloud API token) the token may be a reference. Other credentials made of several parts (a GitHub App private key with its IDs, an Entra ID service principal, an SSH key with its passphrase) cannot be references yet. In the Connectors hub, put the reference in **Credential as a Vault/OpenBao reference** (`config.credential_ref`) instead of the credential.
- Webhook signing secrets and worker tokens are generated by PATHOS and are never references.
- One Vault/OpenBao connection per organization (**Connectors → IAM & Secrets**). Its own AppRole secret ID is stored encrypted in PATHOS (it cannot be a reference to itself).

## How it works

1. An administrator creates the Vault/OpenBao connector: address, optional namespace (Vault Enterprise / HCP), auth method, **allowed path prefix** (strongly recommended, for example `secret/pathos`), optional private CA bundle, optional canary reference for the health check.
2. In any connector, the administrator enters `vault:secret/pathos/scm/github#token` in the token field instead of the token.
3. At use time (test, sync, clone credential for a scan, delivery), PATHOS:
   1. refuses the reference if it is outside the allowed prefix (`PTH-CONN-1607`), without contacting Vault;
   2. logs in (`POST /v1/auth/<mount>/login`) unless it holds a valid Vault token in memory;
   3. reads `GET /v1/<mount>/data/<path>` with `X-Vault-Token` (and `X-Vault-Namespace`);
   4. returns field `<key>` to the code that needs it, and forgets it.

Vault API references (checked 2026-11-20): [AppRole](https://developer.hashicorp.com/vault/api-docs/auth/approle), [Kubernetes auth](https://developer.hashicorp.com/vault/api-docs/auth/kubernetes), [KV v2](https://developer.hashicorp.com/vault/api-docs/secret/kv/kv-v2), [sys/health](https://developer.hashicorp.com/vault/api-docs/system/health), [namespaces](https://developer.hashicorp.com/vault/docs/enterprise/namespaces).

## Trust model

| Question | Answer |
|---|---|
| What does PATHOS store? | The reference string (encrypted like any credential), the Vault address and settings (configuration), and for AppRole the **secret ID** (encrypted, write-only). Kubernetes auth stores no secret: the pod's service account token is read from `/var/run/secrets/kubernetes.io/serviceaccount/token` at login. |
| Where does the secret value live in PATHOS? | Only in the memory of the api or jobs process, for the duration of the call that uses it. It is **never written to disk**, to the database, to logs or to an AI prompt, and **never cached**: a rotated secret is used at its next use. |
| What is cached? | Only the Vault **client token**, in memory, until 30 seconds before its lease ends (at most one hour). A restart discards it. |
| Who can make PATHOS read a path? | Anyone who can manage a connector can type a reference. PATHOS can read whatever its Vault policy allows, so: give the PATHOS role a policy with `read` on `<mount>/data/<prefix>/*` only, and set the same **allowed path prefix** on the connector. PATHOS then refuses other paths before contacting Vault. |
| What if PATHOS is compromised? | An attacker with the PATHOS master key and database, or with code execution in the api/jobs containers, can log in as the PATHOS role and read everything that role's policy allows. References reduce *what is stored in PATHOS* and make rotation and revocation central; they do not protect against a compromised PATHOS server. Keep the policy narrow, set `secret_id_ttl`, `secret_id_num_uses` and `secret_id_bound_cidrs`/`token_bound_cidrs` on the AppRole, and prefer Kubernetes auth when PATHOS runs in Kubernetes. |
| Transport | `https` only (plain `http` only with the development flag), TLS verified, optional private CA bundle added to the system trust store. Internal addresses need **allow private network** on the connector. Requests carry no secret in the URL. |
| Errors | Error messages carry Vault's own error strings (truncated) and never the secret ID, the token or a secret value. |

Least-privilege policy example:

```hcl
path "secret/data/pathos/*" {
  capabilities = ["read"]
}
```

AppRole for PATHOS (example):

```bash
bao auth enable approle    # or: vault auth enable approle
bao write auth/approle/role/pathos token_policies=pathos-read secret_id_ttl=720h token_ttl=15m \
    secret_id_bound_cidrs=10.20.0.0/24 token_bound_cidrs=10.20.0.0/24
bao read auth/approle/role/pathos/role-id
bao write -f auth/approle/role/pathos/secret-id
```

## Health check

The connector's health check calls `GET /v1/sys/health` (sealed or not initialized: `PTH-CONN-1604`; standby nodes count as healthy), logs in, then reads the canary reference if one is set (its value is discarded).

## Implementation status

- Implemented (M2): reference parsing and resolution, AppRole and Kubernetes login, namespaces, path prefix guard, private CA, health check, error codes, resolution inside the secret store for every connector credential kind listed under Scope. Tested against an OpenBao 2.4 dev server.
- Wiring: the Vault/OpenBao connector is a kind of the Connectors registry; until the Connectors hub is enabled the resolver reports `PTH-CONN-1608`.
- Planned: multi-part credentials as references, AWS Secrets Manager, Azure Key Vault and GCP Secret Manager references (`PTH-CONN-1610`, `1611`), response-wrapped secret ID delivery.

## Troubleshooting

| Code | Meaning | Fix |
|---|---|---|
| [PTH-CONN-1601](../troubleshooting/conn.md#PTH-CONN-1601) | AppRole login refused | Generate a new secret ID; check the role's CIDR bindings |
| [PTH-CONN-1602](../troubleshooting/conn.md#PTH-CONN-1602) | The Vault policy denies the path | Grant `read` on `<mount>/data/<prefix>/*` (KV v2 paths include `data/`) |
| [PTH-CONN-1603](../troubleshooting/conn.md#PTH-CONN-1603) | Namespace not found | Correct or clear the namespace |
| [PTH-CONN-1604](../troubleshooting/conn.md#PTH-CONN-1604) | Vault is sealed | Unseal Vault |
| [PTH-CONN-1605](../troubleshooting/conn.md#PTH-CONN-1605) | Kubernetes auth role does not match the service account | Bind the role to the PATHOS service account and namespace, or use AppRole |
| [PTH-CONN-1606](../troubleshooting/conn.md#PTH-CONN-1606) | Secret or key not found | Check the path and key (case-sensitive) |
| [PTH-CONN-1607](../troubleshooting/conn.md#PTH-CONN-1607) | Reference outside the allowed prefix | Move the secret under the prefix |
| [PTH-CONN-1608](../troubleshooting/conn.md#PTH-CONN-1608) | No Vault/OpenBao connection | Create or enable the connector, or enter the secret value instead |
| [PTH-CONN-1004](../troubleshooting/conn.md#PTH-CONN-1004) | Vault's certificate is not trusted | Add the private CA bundle to the connector |
